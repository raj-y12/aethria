## 0. Verdict

**This is a well-engineered codebase, not a fragile one.** The discipline is real: strict multi-tenant scoping, graceful degradation everywhere, comprehensive CI, near-perfect frontend accessibility/TS hygiene, a documented multi-instance scaling seam. Most "AI-built app" failure modes are absent.

The brutal truth is in the **long tail**: a handful of god-files, an over-broad exception culture that can mask real failures, LLM clients with no timeout/retry governance, no React error boundary, a single-vendor retrieval dependency with a hard monthly cap, and non-reproducible Python builds. None are fatal; together they're the difference between "works on the demo" and "bulletproof."

**Overall: B+ / A-.** The path to A+ is below, sequenced.

## 1. Severity-Ranked Findings

### P0 — Fix before you scale users or spend

**P0-1. LLM clients have no timeout or retry governance (reliability + cost).**
`OpenAI(api_key=...)` is instantiated in **6 places** with SDK defaults (600s timeout, 2 silent retries) and no shared config:
`scout/base.py:101`, `reviewer/base.py:492`, `partner/decision.py:252`, `meta/mutator.py:170`, `fund_thesis_ops.py:51`, `fund_thesis_ops.py:93`.
Calls are correctly offloaded via `run_in_executor` (good — no event-loop block, `scout/base.py:1162`), but with `MAX_CONCURRENT_PIPELINE_CYCLES=1` on a small instance, **one slow call can hold a pipeline stage for up to 10 minutes × retries**, and silent retries double cost invisibly.
**Fix:** one factory (`build_openai_client()`) with explicit `timeout=(connect, read)`, `max_retries`, and a per-call cost log. Replace all 6 call sites. ~1 hour, high leverage.

**P0-2. No React error boundary — any render error = white screen.**
Zero `ErrorBoundary` / `componentDidCatch` in the entire frontend (grep over `app-front-end/src` returns nothing). A single thrown error in any component (a malformed memo, a null field from the API) blanks the whole app with no recovery, no telemetry.
**Fix:** wrap the app shell (`AppFrame.tsx`) and each major route in an error boundary that renders a fallback + reports to your logging. Half a day.

**P0-3. Single-vendor retrieval with a hard cap is a product-level single point of failure.**
All web retrieval funnels through Tavily (`utils/retrieval_grounding.py` → `utils/tavily_client.py`); the `provider` field is cosmetic (always `"tavily"`, `retrieval_grounding.py:78,142`). When the monthly free credits run out, **the entire discovery + lookup product silently degrades to `NOT_FOUND`** (observed live during this session: HTTP 432). The resolver degrades gracefully, which *hides* the outage rather than surfacing it.
**Fix:** the provider seam you already sketched (`RETRIEVAL_PROVIDER=tavily|brave|searxng|ddg`) + a fallback chain + a loud alert when the primary 4xx's on quota. This is the one finding that already has a decision pending.

### P1 — Fix soon; these compound as the app grows

**P1-1. Over-broad exception culture (288 `except Exception`).**
288 broad catches in non-test backend (`grep "except Exception"`). Only 3 are silently `pass` (good), but "catch-all-and-log-and-continue" at this density **masks real bugs as warnings** and makes failures look like success to callers. The pipeline especially swallows and proceeds (`pipeline_runner.py`), so a broken stage can produce a plausible-but-wrong startup row.
**Fix:** audit for the ~20 hottest paths; narrow to specific exceptions; for the rest, ensure the *caller* can tell success from degraded (return a status, not a silent None). Don't chase all 288 — target the pipeline + storage + scoring paths.

**P1-2. God-files hurt change-safety (yours and an AI's).**
`api.py` 2,498 LOC / 27 routes / 75 functions; `partner/decision.py` 1,876; `supabase_storage.py` 1,293; `scout/base.py` 1,198; frontend `InvestmentMemoContent.tsx` 1,339; `SettingsPage.tsx` 1,104; `system/internals.tsx` 1,009. A `routers/` package already exists (`routers/deps.py`, an analytics router) — the pattern is there but most routes never moved.
**Fix:** extract `api.py` routes into domain routers (lookup, startups, settings, meta, agents, admin) behind the existing pattern; split the three 1k+ frontend files by responsibility. Mechanical, low-risk, big readability/edit-reliability win.

**P1-3. Runtime schema-drift fallbacks mean migrations aren't trusted in prod.**
`supabase_storage.py:276-330` catches "column missing" errors for `agent_trace`, `unresolved_at`, and queue-awareness columns, pops the field, and retries — logging "apply migration X." This is defensive code compensating for **migrations that may not be applied** (contradicts the CLAUDE.md "migrations must be applied" rule). It's clever, but it silently drops data and hides drift.
**Fix:** a startup migration-state check that fails fast (or loudly warns) if expected columns are absent, so drift is an ops alert, not a silent data loss. Then the fallbacks can be removed.

**P1-4. Non-reproducible Python builds.**
`backend/requirements.txt` has **0 pinned, 10 `>=` deps** (`openai>=1.12.0`, `fastapi>=0.115.0`, …) and no lock file. CI caches by hash of `requirements.txt`, but `>=` means the same file resolves to different versions over time — a transitive/major bump can break prod with no code change. (Frontend is fine: `package-lock.json` present, `npm ci` in CI.)
**Fix:** adopt `uv`/`pip-tools` and commit a fully-pinned `requirements.lock`; install from the lock in CI and Docker.

### P2 — Hardening / quality

- **P2-1. 32 `print()` calls in non-test backend** bypass structured logging (`grep "^\s*print("`). Convert to `logger`.
- **P2-2. Frontend test coverage is thin** (9 test files for 20.6k LOC). Vitest + Testing-Library + Playwright are wired and run in CI (good foundation), but the biggest surfaces — `InvestmentMemoContent`, `WorkGrid`, `useDispatchLookup`, scoring components — are untested. Add component/interaction tests for the deal-flow grid and memo render paths.
- **P2-3. Main JS bundle is heavy** (~471 KB / 145 KB gzip initial, plus `index.es` 158 KB, `jspdf` 386 KB, `html2canvas` 201 KB). `jspdf` is correctly lazy-loaded (`memoIcPack.ts:324`) and routes are split (`App.tsx:14-15`) — but audit whether Clerk/framer/tanstack are all in the initial chunk and trim/defer what isn't needed for first paint.
- **P2-4. Verify cost governance is enforced, not just defined.** `CostController` exists per CLAUDE.md; confirm every LLM call site actually checks it (the 6 ungoverned `OpenAI()` sites in P0-1 suggest call-site discipline may have gaps).

### P3 — Polish

- Centralize the 6 OpenAI instantiations (folds into P0-1).
- `partner/decision.py` is 1,876 lines but the "thresholds in JSON" rule **holds** — the numeric literals are input sanitization/clamps, not business thresholds, and `core/policy_resolver.py` does read the versioned JSON. Non-finding; size is the only issue (P1-2).

## 3. What Is Genuinely Strong — Do Not "Refactor" These

- The **tenant-scoping invariant** is consistently honored. Don't loosen it.
- The **accessibility and TS hygiene** are top-decile. Keep `--max-warnings 0`.
- The **graceful-degradation contract** in the resolver (PARTIAL/LOW_CONFIDENCE/NEEDS_REVIEW with explicit found/missing) is genuinely good product thinking. The fix is to make outages *loud*, not to remove the grace.
- The **CI matrix** is more thorough than most funded startups.
- The **event-bus backplane seam** (`event_bus.py`) shows you've already thought about multi-instance scaling correctly.

## 4. Bulletproofing Roadmap (sequenced for max gain / min risk)

**Week 1 — Stop silent failure (all P0):**
1. OpenAI client factory with timeout/retry/cost-log; replace 6 call sites (P0-1).
2. React error boundaries on shell + routes with reporting (P0-2).
3. Retrieval provider seam + fallback + loud quota alert (P0-3). *(Decision already pending — metered Tavily or SearXNG-on-existing-box per the provider discussion.)*

**Week 2 — Make failure legible (P1-1, P1-3, P1-4):**
4. Narrow the ~20 hottest broad excepts; give callers a degraded-vs-ok status.
5. Startup migration-state check that alerts on drift; then delete the pop-column fallbacks.
6. Pin Python deps with a committed lock; install from lock in CI + Docker.

**Week 3 — Reduce blast radius of change (P1-2, P2-2):**
7. Split `api.py` into domain routers; split the three 1k+ frontend files.
8. Component/interaction tests for `WorkGrid`, `InvestmentMemoContent`, `useDispatchLookup`.

**Ongoing — polish:** `print()`→logger, bundle trim, coverage gates in CI.

**Discipline to adopt:** treat every new `except Exception` and every new 600-LOC file as a code-review red flag. Those two habits alone prevent 80% of the regression risk this audit found.

## 5. Honest Limits of This Audit

- **Static + sampled, not exhaustive.** 54k LOC was surveyed by structure, size, and pattern-grep with targeted deep reads of the highest-signal files — not a line-by-line read of every file. The findings are real and cited; absence of a finding in an unread file is not proof of its absence.
- **No live runtime verification.** Tavily's quota was exhausted during the session (HTTP 432), so end-to-end behavior against real retrieval could not be exercised. Load, race, and production-config behavior are unaudited.
- **No dependency CVE scan** was run; P1-4 (unpinned deps) means a CVE audit would be point-in-time anyway. Add `pip-audit`/`npm audit` to CI.
